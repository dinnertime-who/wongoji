# 기획 — 로그인 없는 원고 관리

> 작성: 2026-08-11. 저장소는 localStorage를 그대로 쓴다(IndexedDB 검토 결과는 아래 0절).

## 0. 전제 — 왜 localStorage 그대로인가

바꿀 이유로 흔히 드는 두 가지가 실측에서 성립하지 않았다.

| 항목 | 값 |
|---|---|
| 70매 원고(14,007자) JSON | **25 KB** |
| localStorage 쓰기 | **0.11 ms** |
| localStorage 상한 | **5 MB** (`QuotaExceededError`) |
| 들어가는 원고 수 | **약 200편** |

용량도 속도도 문제가 아니다. IndexedDB는 지금 얻는 것 없이 복잡도만 늘린다.
**첨부 파일이 생기거나, 색인 조회가 필요해지거나, 장편(800매 ≈ 300KB)을 여러 편
두게 되면** 그때 옮긴다.

---

## 1. 데이터 모델

### 키 구조

```
wongoji:v1:index          목록과 메타데이터
wongoji:v1:doc:<id>       Tiptap 문서 (원고 하나)
wongoji:v1:last           마지막으로 연 원고 id
```

```jsonc
// wongoji:v1:index
{
  "version": 1,
  "items": [
    {
      "id": "k3f9a2",
      "title": "감나무 있는 마당",
      "goal": 70,          // 목표 매수. 0이면 목표 없음
      "chars": 14007,      // 목록에서 보여줄 값 — 문서를 안 열고도 알 수 있게
      "sheets": 71,
      "createdAt": 1786440000000,
      "updatedAt": 1786440900000
    }
  ]
}
```

### 왜 목록과 문서를 나누는가

- **저장 비용** — 한 덩어리에 다 넣으면 글자 하나 칠 때마다 전체(원고 200편이면 5MB)를 다시 쓴다. 원고별로 나누면 25KB만 쓴다
- **목록 비용** — 목록을 그리려고 모든 문서를 파싱할 이유가 없다. 분량 같은 파생값은 저장할 때 색인에 함께 적어 둔다

### id

`crypto.randomUUID()`는 길어서 키가 지저분해진다. 짧은 무작위 문자열(6~8자)이면
충분하다 — 한 브라우저 안에서만 유일하면 된다.

## 2. 기존 원고 이어받기

지금 키는 이렇다.

```
wongoji:draft  wongoji:title  wongoji:goal  wongoji:mainPane
```

새 코드가 처음 뜰 때 색인이 없고 `wongoji:draft`가 있으면, **그것을 원고 1편으로
옮긴다.** 옮긴 뒤에도 **옛 키는 지우지 않는다** — 한동안 남겨 두었다가 나중에
정리한다. 서버 사본이 없는 마당에 되돌릴 길을 스스로 없앨 이유가 없다.

`mainPane`은 원고와 무관한 화면 설정이라 그대로 둔다.

---

## 3. 화면

### 경로

```
/            → 마지막 원고로 보낸다. 없으면 새로 만들어 연다
/w/$id       → 원고 편집 (지금 화면)
/w           → 원고 목록
```

라우터가 이미 있으니 원고마다 주소를 준다. 얻는 것:

- 뒤로 가기가 원고 전환으로 동작한다
- **탭 여러 개에 원고를 각각 띄울 수 있다** — 초고와 고쳐 쓴 것을 나란히 두는 건
  글 쓰는 사람에게 흔한 일이다
- 북마크가 된다 (같은 브라우저 안에서만 유효하다는 한계는 있다)

`/`에서 목록을 먼저 보여주면 원고가 한두 편일 때 매번 한 단계가 더 생긴다.
마지막 원고로 바로 보내고, 목록은 따로 간다.

### 헤더

제목 왼쪽에 원고 전환 드롭다운을 둔다 — 현재 제목 + 최근 몇 편 + "모든 원고".
지금 제목 바에 있는 제목 입력칸은 그대로 둔다(원고지 첫 장에 조판되는 값이라
성격이 다르다).

### 목록 화면

원고마다: 제목 · 분량(`62 / 70매`) · 마지막 수정 · 복제 · 삭제 · 내보내기.
정렬은 최근 수정순.

## 4. 반드시 처리할 것

**1. 저장 실패를 삼키지 않는다.** 지금 코드는 디바운스된 타이머 안에서
`localStorage.setItem`을 부르고 결과를 보지 않는다. 상한(5MB)에 닿으면
`QuotaExceededError`가 나는데, **사용자는 계속 쓰고 아무것도 저장되지 않는다.**
이건 원고 관리를 붙이기 전에도 이미 있는 위험이다. 실패하면 화면에 분명히 알리고
내보내기를 권해야 한다.

**2. 삭제는 되돌릴 수 있어야 한다.** 서버 사본이 없으니 삭제는 영구 소실이다.
지운 원고를 `wongoji:v1:trash:<id>`로 옮겨 두고 목록에서 되살릴 수 있게 한다.
비우기는 사용자가 직접 한다.

**3. 탭 두 개가 색인을 동시에 고칠 수 있다.** 각자 다른 원고를 열어도 색인 키는
하나다. 읽고-고치고-쓰는 사이에 다른 탭이 쓰면 덮인다.
- 색인을 쓸 때는 **그 자리에서 다시 읽어 병합**한다 (메모리에 든 오래된 사본을
  통째로 쓰지 않는다)
- `storage` 이벤트를 들어 다른 탭의 변경을 반영한다
- 같은 원고를 두 탭에서 열면 서로 덮어쓴다 — 이건 막지 말고 **알려주는 선**에서
  그친다 (다른 탭에서 열려 있다는 표시)

**4. `navigator.storage.persist()`를 부른다.** 지원을 확인했다(`true`). 허용되면
용량 압박 상황에서 브라우저가 함부로 지우지 못한다. 서버 사본이 없는 지금
구조에서는 용량보다 이쪽이 중요하다.

**5. 저장되었음을 보인다.** 원고가 여러 편이 되면 "지금 것이 저장됐나"가 늘
불안해진다. 마지막 저장 시각을 조용히 표시한다.

---

## 5. 순서

1. **저장 실패 처리 + `persist()`** — 원고 관리와 무관하게 지금 있는 위험이다. 먼저
2. **저장소 계층 분리** — `src/lib/store/`로 키 조작을 모은다. 지금은 라우트에
   흩어져 있어 원고가 여러 편이 되면 감당이 안 된다
3. **마이그레이션 + 원고 1편으로 동작** — 화면은 그대로, 안쪽만 새 구조로
4. **경로 분리** (`/w/$id`)
5. **목록 화면과 전환 드롭다운**
6. **복제 · 삭제(휴지통)**

3번까지 하면 겉보기는 지금과 같고 구조만 바뀐다. 되돌리기 쉬운 지점이다.

---

## 6. 정할 것

**공모전 정보를 여기에 둘 것인가.** 마감일·응모처·제출 여부 같은 것. 이미 노션으로
관리하고 계셔서 **중복이 될 것 같다.** 안 넣는 쪽을 권하고, 대신 목록에 메모 한 줄
정도만 두는 것도 방법이다.

**원고를 폴더로 묶을 것인가.** 편수가 적으면 최근순 목록으로 충분하다. 지금은 넣지
않는 쪽을 권한다.

**같은 원고를 두 탭에서 열 때 어떻게 할 것인가.** 막을지, 알리기만 할지.
알리기만 하는 쪽을 권한다 — 막으면 탭을 잘못 닫았을 때 곤란해진다.
