# 기획 — 로그인 없는 원고 관리

> 작성: 2026-08-11. 저장소는 localStorage를 그대로 쓴다(IndexedDB 검토 결과는 아래 0절).

## 0. 전제 — 왜 localStorage 그대로인가

바꿀 이유로 흔히 드는 두 가지가 실측에서 성립하지 않았다.

| 항목 | 값 |
|---|---|
| 70매 원고(14,007자) JSON | **25 KB** |
| localStorage 쓰기 | **0.11 ms** |
| localStorage 상한 | **5 MB** (`QuotaExceededError`) |
| 들어가는 원고 수 | **약 200편** |

용량도 속도도 문제가 아니다. IndexedDB는 지금 얻는 것 없이 복잡도만 늘린다.
**첨부 파일이 생기거나, 색인 조회가 필요해지거나, 장편(800매 ≈ 300KB)을 여러 편
두게 되면** 그때 옮긴다.

## 1. 데이터 모델

### 키 구조

```
wongoji:v1:index          폴더 나무 · 원고 목록 · 휴지통
wongoji:v1:doc:<id>       Tiptap 문서 (원고 하나)
wongoji:v1:last           마지막으로 연 원고 id
```

```jsonc
// wongoji:v1:index
{
  "version": 1,
  "folders": [
    { "id": "f1", "name": "신춘문예", "parentId": null },
    { "id": "f2", "name": "2026",     "parentId": "f1" }
  ],
  "docs": [
    {
      "id": "d1",
      "title": "감나무 있는 마당",
      "folderId": "f2",     // null이면 맨 바깥
      "goal": 70,           // 목표 매수. 0이면 목표 없음
      "chars": 14007,       // 목록에서 보여줄 값 — 문서를 안 열고도 알 수 있게
      "sheets": 71,
      "createdAt": 1786440000000,
      "updatedAt": 1786440900000
    }
  ],
  "trash": [
    { "kind": "doc",    "id": "d9", "folderId": "f2",  "deletedAt": 1786000000000 },
    { "kind": "folder", "id": "f7", "parentId": "f1",  "deletedAt": 1786000000000 }
  ]
}
```

### 폴더는 나무를 중첩해서 담지 않는다

`parentId`를 가진 **평평한 배열**로 둔다. 나무는 화면에서 만든다.

JSON을 중첩하면 폴더 하나를 옮길 때마다 가지를 잘라 붙여야 하고, 저장할 때마다
깊은 구조를 통째로 다시 쓴다. 평평하게 두면 **이동이 필드 하나 바꾸는 일**이 된다.

두 가지를 막아야 한다.

- **자기 자손 안으로 옮기기** — 순환이 생겨 나무가 끊긴다. 조상 사슬을 훑어 막는다
- **없는 부모 가리키기** — 부모가 사라졌으면 맨 바깥으로 올린다 (읽을 때 정리)

### 목록과 문서를 나누는 이유

- **저장 비용** — 한 덩어리에 다 넣으면 글자 하나 칠 때마다 전체(원고 200편이면 5MB)를 다시 쓴다. 원고별로 나누면 25KB만 쓴다
- **목록 비용** — 목록을 그리려고 모든 문서를 파싱할 이유가 없다. 분량 같은 파생값은 저장할 때 색인에 함께 적어 둔다

### 휴지통 — 30일

지운 것은 `trash`에 자리만 옮긴다. **문서 본문(`doc:<id>`)은 그대로 둔다.**
앱이 뜰 때 `deletedAt`이 30일을 넘은 항목을 비우고, 그때 본문 키도 함께 지운다.

- **폴더를 지우면 그 아래 전부**가 함께 휴지통으로 간다. 되살릴 때도 함께 온다
- 되살릴 자리(원래 폴더)가 사라졌으면 **맨 바깥으로** 올린다
- 30일 계산은 앱을 열 때만 한다. 몇 달 만에 열면 그때 정리된다 — 그 사이 용량을
  차지하지만, 되살릴 기회를 남기는 편이 낫다

### id

`crypto.randomUUID()`는 길어서 키가 지저분해진다. 짧은 무작위 문자열(6~8자)이면
충분하다 — 한 브라우저 안에서만 유일하면 된다.

## 2. 기존 원고 이어받기

지금 키는 이렇다.

```
wongoji:draft  wongoji:title  wongoji:goal  wongoji:mainPane
```

새 코드가 처음 뜰 때 색인이 없고 `wongoji:draft`가 있으면, **그것을 원고 1편으로
옮긴다.** 옮긴 뒤에도 **옛 키는 지우지 않는다** — 한동안 남겨 두었다가 나중에
정리한다. 서버 사본이 없는 마당에 되돌릴 길을 스스로 없앨 이유가 없다.

`mainPane`은 원고와 무관한 화면 설정이라 그대로 둔다.

## 3. UI

### 전제 — 편집 화면에 나무를 상주시키지 않는다

에디터 폭은 이미 빠듯하다. 2열로 바꾸면서 한 줄 78자에서 **36자**로 줄었다.
여기에 사이드바를 상주시키면 27자쯤으로 떨어져, 앞서 불편하다고 했던 23자에
가까워진다. **글을 쓰는 동안에는 폴더 나무가 필요 없다.**

그래서 나무는 목록 화면에만 두고, 편집 화면에서는 빵부스러기와 드롭다운으로
왔다 갔다 한다.

### 경로

```
/            → 마지막 원고로 보낸다. 없으면 새로 만들어 연다
/w/$id       → 원고 편집 (지금 화면)
/w           → 원고 목록 (폴더 나무)
/w?trash     → 휴지통
```

원고마다 주소를 주면 뒤로 가기가 원고 전환이 되고, **탭 여러 개에 원고를 각각
띄울 수 있다** — 초고와 고쳐 쓴 것을 나란히 두는 건 글 쓰는 사람에게 흔한 일이다.

`/`에서 목록을 먼저 보여주면 원고가 한두 편일 때 매번 한 단계가 더 생긴다.

### 편집 화면 — 헤더만 바뀐다

```
┌─────────────────────────────────────────────────────────┐
│ 200자 원고지   신춘문예 / 2026 / 감나무 있는 마당 ▾  [파일] │
├─────────────────────────────────────────────────────────┤
│  [제목                          ]  목표 70 매            │
│  62 / 70매   1,600자 남음   14,007자 · 82장             │
│  ▓▓▓▓▓▓▓▓▓▓▓▓░░░░░░                                     │
├──────────────────────────┬──────────────────────────────┤
│  원고                     │  원고지                       │
```

- **빵부스러기**가 곧 현재 위치다. 폴더 이름을 누르면 그 폴더의 목록으로 간다
- **`▾`를 누르면** 최근 원고 5편 + `모든 원고` + `새 원고`. 자주 오가는 두세 편은
  이것으로 충분하다
- 지금 제목 바의 제목 입력칸은 그대로 둔다 — **원고지 첫 장에 조판되는 값**이라
  성격이 다르다. 다만 그 값이 목록의 이름이 된다

### 목록 화면 — 여기에 나무를 둔다

```
┌──────────────────────────────────────────────────────────┐
│ ← 원고            [새 폴더]  [새 원고]                     │
├────────────────────┬─────────────────────────────────────┤
│ ▾ 📁 신춘문예       │  신춘문예 / 2026                     │
│   ▾ 📁 2026        │  ┌───────────────────────────────┐  │
│       감나무 있는…  │  │ 📁 초고                    ⋯  │  │
│     📁 초고        │  ├───────────────────────────────┤  │
│   ▸ 📁 2025        │  │ 📄 감나무 있는 마당         ⋯  │  │
│ ▸ 📁 백일장        │  │    62 / 70매 · 3일 전         │  │
│   📄 (폴더 밖 원고) │  └───────────────────────────────┘  │
│ ─────────────────  │                                     │
│ 🗑 휴지통 2         │                                     │
└────────────────────┴─────────────────────────────────────┘
```

- **왼쪽 나무**는 폴더만 보여준다(원고까지 넣으면 금방 길어진다). 맨 바깥 원고는
  예외로 보여 준다
- **오른쪽**은 고른 폴더의 내용. 폴더가 먼저, 그다음 원고
- 원고 줄에는 **분량과 마지막 수정 시각**. 목록용 값을 색인에 넣어 두는 이유다
- `⋯` 메뉴: 이름 바꾸기 · **이동** · 복제 · 내보내기 · 삭제

### 이동은 끌어놓기 대신 고르기로

끌어놓기는 손이 많이 가고 모바일에서 특히 어렵다. 먼저 **`이동` → 폴더 고르기
다이얼로그**로 만든다. 자기 자손은 목록에서 빼서 순환을 애초에 막는다.

끌어놓기는 나중에 얹는다. 얹더라도 `이동` 메뉴는 남긴다 — 모바일과 키보드 사용자에게 필요하다.

### 휴지통

```
┌──────────────────────────────────────────────────────────┐
│ ← 휴지통                                    [전부 비우기]  │
├──────────────────────────────────────────────────────────┤
│ 📄 옛 원고            신춘문예/2025에 있던 것             │
│                       23일 뒤 삭제      [되살리기] [지금 삭제] │
│ 📁 습작 (원고 3편)    맨 바깥에 있던 것                    │
│                       11일 뒤 삭제      [되살리기] [지금 삭제] │
└──────────────────────────────────────────────────────────┘
```

- **남은 날을 적는다.** "30일 뒤 삭제"라고만 하면 언제 지워지는지 알 수 없다
- 폴더는 **몇 편이 함께 들어 있는지** 보여 준다. 되살리면 함께 온다
- `지금 삭제`와 `전부 비우기`는 되돌릴 수 없으므로 한 번 더 묻는다

### 모바일

- 목록 화면은 **나무와 내용을 한 화면에 두지 않는다.** 폴더를 누르면 그 안으로
  들어가고, 빵부스러기로 되돌아온다 (파일 앱과 같은 방식)
- 편집 화면 헤더의 빵부스러기는 길어지면 앞을 줄인다 — `… / 2026 / 감나무…`

## 4. 반드시 처리할 것

**1. 저장 실패를 삼키지 않는다.** 지금 코드는 디바운스된 타이머 안에서
`localStorage.setItem`을 부르고 결과를 보지 않는다. 상한(5MB)에 닿으면
`QuotaExceededError`가 나는데, **사용자는 계속 쓰고 아무것도 저장되지 않는다.**
이건 원고 관리를 붙이기 전에도 이미 있는 위험이다. 실패하면 화면에 분명히 알리고
내보내기를 권해야 한다.

**2. 삭제는 되돌릴 수 있어야 한다.** 서버 사본이 없으니 삭제는 영구 소실이다.
색인의 `trash`로 자리만 옮기고 30일 뒤 비운다(1절). 목록에서 되살릴 수 있게 하고,
`지금 삭제`처럼 되돌릴 수 없는 것은 한 번 더 묻는다.

**3. 탭 두 개가 색인을 동시에 고칠 수 있다.** 각자 다른 원고를 열어도 색인 키는
하나다. 읽고-고치고-쓰는 사이에 다른 탭이 쓰면 덮인다.
- 색인을 쓸 때는 **그 자리에서 다시 읽어 병합**한다 (메모리에 든 오래된 사본을
  통째로 쓰지 않는다)
- `storage` 이벤트를 들어 다른 탭의 변경을 반영한다
- 같은 원고를 두 탭에서 열면 서로 덮어쓴다 — 이건 막지 말고 **알려주는 선**에서
  그친다 (다른 탭에서 열려 있다는 표시)

**4. `navigator.storage.persist()`를 부른다.** 지원을 확인했다(`true`). 허용되면
용량 압박 상황에서 브라우저가 함부로 지우지 못한다. 서버 사본이 없는 지금
구조에서는 용량보다 이쪽이 중요하다.

**5. 저장되었음을 보인다.** 원고가 여러 편이 되면 "지금 것이 저장됐나"가 늘
불안해진다. 마지막 저장 시각을 조용히 표시한다.

## 5. 순서

1. **저장 실패 처리 + `persist()`** — 원고 관리와 무관하게 지금 있는 위험이다. 먼저
2. **저장소 계층 분리** — `src/lib/store/`로 키 조작을 모은다. 지금은 라우트에
   흩어져 있어 원고가 여러 편이 되면 감당이 안 된다
3. **마이그레이션 + 원고 1편으로 동작** — 화면은 그대로, 안쪽만 새 구조로
4. **경로 분리** (`/w/$id`)
5. **폴더 나무 + 목록 화면 + 전환 드롭다운**
6. **이동 · 복제 · 삭제(휴지통 30일)**

3번까지 하면 겉보기는 지금과 같고 구조만 바뀐다. 되돌리기 쉬운 지점이다.

## 6. 정해진 것

- **공모전 정보는 넣지 않는다.** 노션으로 관리하고 있어 중복이 된다
- **폴더는 중첩을 허용한다.** 깊이 제한은 두지 않되, 빵부스러기가 길어지면 앞을 줄인다
- **휴지통은 30일.** 앱을 열 때 지난 것을 비운다
- **같은 원고를 두 탭에서 열면 막지 않고 알리기만 한다** — 막으면 탭을 잘못 닫았을 때 곤란해진다
- **원고 이동은 고르기 다이얼로그로.** 끌어놓기는 나중에

## 7. 아직 답이 없는 것

- **나무가 깊어질 때 왼쪽 폭.** 깊이 4~5단이 되면 접히는 폭으로는 모자란다.
  들여쓰기를 줄이거나 가로 스크롤을 두는 선에서 보고 정한다
- **원고를 폴더 밖에 두는 것을 허용할지.** 지금 설계는 허용한다(`folderId: null`).
  강제로 폴더에 넣게 하면 정리는 깔끔하지만 새 원고를 만들 때 한 단계가 늘어난다
