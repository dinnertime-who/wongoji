# 기획 — 로그인 없는 원고 관리

> 작성: 2026-08-11. 저장소는 localStorage를 그대로 쓴다.

## 0. 전제 — 왜 localStorage 그대로인가

바꿀 이유로 흔히 드는 두 가지가 실측에서 성립하지 않았다.

| 항목 | 값 |
|---|---|
| 70매 원고(14,007자) JSON | **25 KB** |
| localStorage 쓰기 | **0.11 ms** |
| localStorage 상한 | **5 MB** (`QuotaExceededError`) |
| 들어가는 원고 수 | **약 200편** |

용량도 속도도 문제가 아니다. IndexedDB는 지금 얻는 것 없이 복잡도만 늘린다.
**첨부 파일이 생기거나, 색인 조회가 필요해지거나, 장편(800매 ≈ 300KB)을 여러 편
두게 되면** 그때 옮긴다.

## 1. 데이터 모델

### 키 구조

```
wongoji:v1:index          폴더 트리 · 원고 목록 · 휴지통
wongoji:v1:doc:<id>       Tiptap 문서 (원고 하나)
wongoji:v1:last           마지막으로 연 원고 id
```

### materialized path

부모 id를 들고 다니는 대신 **조상 사슬을 경로 문자열로 박아 둔다.**

```jsonc
{
  "version": 1,
  "folders": [
    { "id": "f1", "name": "신춘문예", "path": "/" },
    { "id": "f2", "name": "2026",     "path": "/f1/" },
    { "id": "f3", "name": "초고",     "path": "/f1/f2/" }
  ],
  "docs": [
    {
      "id": "d1",
      "title": "감나무 있는 마당",
      "path": "/f1/f2/",    // "/"이면 맨 위(root)
      "goal": 70,           // 목표 매수. 0이면 목표 없음
      "chars": 14007,       // 목록에서 보여줄 값 — 문서를 안 열고도 알 수 있게
      "sheets": 71,
      "createdAt": 1786440000000,
      "updatedAt": 1786440900000
    }
  ],
  "trash": [
    { "kind": "doc",    "id": "d9", "path": "/f1/f2/", "deletedAt": 1786000000000 },
    { "kind": "folder", "id": "f7", "path": "/f1/", "name": "습작", "deletedAt": 1786000000000 }
  ]
}
```

`path`는 **조상들의 id**를 슬래시로 이은 것이다. `f3`의 전체 경로는 `/f1/f2/f3/`.

`/`는 **보이지 않는 root 폴더**다. 화면에는 폴더로 그리지 않고 그 안의 것들이
사이드바 맨 위에 온다. 원고도 폴더도 여기 놓일 수 있다.

root가 있으면 두 가지가 한꺼번에 풀린다.

- **폴더를 하나도 만들지 않아도 원고를 쓸 수 있다.** 폴더는 필요해질 때 만든다
- **되살릴 자리가 사라졌을 때 갈 곳이 늘 있다.** root는 지워지지 않는다

**이름이 아니라 id를 쓴다.** 이름을 쓰면 폴더 이름을 고칠 때마다 하위 전부를 다시
써야 한다. id면 이름 바꾸기가 값 하나 고치는 일이 된다.

### 왜 mpath인가

구조를 자주 바꾸지 않는다는 전제에서 얻는 게 분명하다.

| 하는 일 | mpath | parentId |
|---|---|---|
| 하위 전부 찾기 (폴더 삭제·이동) | `path.startsWith(prefix)` **한 번** | 재귀로 훑어야 함 |
| 브레드크럼 | path를 쪼개면 끝 | 부모를 타고 거슬러 올라감 |
| 폴더 이름 바꾸기 | 값 하나 | 값 하나 |
| **폴더 옮기기** | **하위 전부의 path를 고쳐야 함** | 값 하나 |

마지막 줄이 mpath의 대가인데 여기서는 문제가 되지 않는다. **색인 전체가 어차피
JSON 한 덩어리라 저장할 때마다 통째로 다시 쓴다.** DB처럼 행을 하나씩 갱신하는
구조가 아니므로 "여러 행을 고친다"는 비용이 없다. 옮기기는 배열을 한 번 훑어
접두사를 바꾸는 것으로 끝난다.

그리고 우리에게 제일 잦은 조회가 **"이 폴더 아래 전부"**다 — 폴더를 지울 때,
휴지통에 넣을 때, 되살릴 때 모두 그것이다.

### 지켜야 할 것

- **자기 자손 안으로 옮기기 금지** — 대상 폴더의 전체 경로가 `/…/자기id/`를
  포함하면 막는다. 순환이 생기면 트리가 끊긴다
- **끊어진 경로 정리** — 경로 중간의 폴더가 사라졌으면 읽을 때 가장 가까운 살아
  있는 조상으로 끌어올린다. 거기까지 없으면 root로. root는 지워지지 않으므로
  갈 곳이 없는 경우는 생기지 않는다

### 목록과 문서를 나누는 이유

- **저장 비용** — 한 덩어리에 다 넣으면 글자 하나 칠 때마다 전체(원고 200편이면 5MB)를 다시 쓴다. 원고별로 나누면 25KB만 쓴다
- **목록 비용** — 목록을 그리려고 모든 문서를 파싱할 이유가 없다. 분량 같은 파생값은 저장할 때 색인에 함께 적어 둔다

### 휴지통 — 30일

지운 것은 `trash`로 자리만 옮긴다. **문서 본문(`doc:<id>`)은 그대로 둔다.**
앱이 뜰 때 `deletedAt`이 30일을 넘은 항목을 비우고, 그때 본문 키도 함께 지운다.

- **폴더를 지우면 그 아래 전부**가 함께 들어간다(`startsWith`로 한 번에 걷어낸다).
  되살릴 때도 함께 온다
- 되살릴 자리가 사라졌으면 가장 가까운 살아 있는 조상으로, 없으면 root로
- 30일 계산은 앱을 열 때만 한다. 몇 달 만에 열면 그때 정리된다 — 그 사이 용량을
  차지하지만 되살릴 기회를 남기는 편이 낫다

### id

`crypto.randomUUID()`는 길어서 경로 문자열이 지저분해진다. 짧은 무작위 문자열
(6~8자)이면 충분하다 — 한 브라우저 안에서만 유일하면 된다.

## 2. 기존 원고 이어받기

지금 키는 이렇다.

```
wongoji:draft  wongoji:title  wongoji:goal  wongoji:mainPane
```

새 코드가 처음 뜰 때 색인이 없고 `wongoji:draft`가 있으면, **root의 원고 1편으로
옮긴다.** 제목이 비어 있으면 `제목 없는 원고`로 둔다. 폴더는 만들지 않는다.

옮긴 뒤에도 **옛 키는 지우지 않는다.** 서버 사본이 없는 마당에 되돌릴 길을 스스로
없앨 이유가 없다. 한동안 두었다가 나중에 정리한다.

`mainPane`은 원고와 무관한 화면 설정이라 그대로 둔다.

---

## 3. 온보딩 — 원고 하나로 시작한다

처음 열었을 때(색인도 없고 옛 원고도 없을 때) 묻지 않고 **root에 원고 하나**를
만들고 바로 연다.

```
📄 제목 없는 원고     ← 사이드바 맨 위. 폴더는 없다
```

**기본 폴더는 만들지 않는다.** 앞선 안에서 기본 폴더가 필요했던 이유는 "원고는
폴더 밖에 둘 수 없다"는 제약 때문이었는데, root가 생기면서 그 제약이 사라졌다.
폴더를 처음부터 하나 만들어 두면 원고가 한 편일 때 괜히 한 단계가 깊어진다.
**폴더는 필요해질 때 사용자가 만든다.**

같은 이유로 **"마지막 폴더는 지울 수 없다"는 규칙도 없앤다.** 폴더를 전부 지워도
원고는 root에 남는다.

## 4. UI

### 사이드바 — 노션처럼 상주하되 접힌다

폭을 재봤다. **사이드바를 가운데 정렬 컨테이너 바깥에 두면** 넓은 화면에서는
지금과 달라지지 않는다.

| 화면 폭 | 사이드바 | 에디터 한 줄 |
|---|---|---|
| 1454px | 240px | **36자** (지금과 같음) |
| 1280px | 240px | 약 33자 |
| 1152px | 240px | 약 28자 |

본문이 `max-w-6xl`(1152px)로 묶여 있어서, 사이드바를 빼고도 1152px가 남는
**1400px 이상에서는 에디터 폭이 그대로다.** 그보다 좁아지면 줄어들므로
**1280px 아래에서는 기본으로 접는다.** 접힘 상태는 기억한다.

```
┌──────────┬──────────────────────────────────────────────┐
│ 원고      │ 200자 원고지  신춘문예 / 2026 / 감나무…  [파일] │
│ [+ 폴더]  ├──────────────────────────────────────────────┤
│          │  [제목                    ]   목표 70 매       │
│ ▾ 신춘문예 │  62 / 70매  1,600자 남음                     │
│  ▾ 2026  │  ▓▓▓▓▓▓▓▓▓▓▓░░░░░                            │
│    감나무… ├───────────────────────┬──────────────────────┤
│    ▸ 초고 │  원고                  │  원고지               │
│  ▸ 2025  │                       │                      │
│ ▸ 백일장  │                       │                      │
│ ───────  │                       │                      │
│ 🗑 휴지통 2│                       │                      │
└──────────┴───────────────────────┴──────────────────────┘
```

- **폴더와 원고를 함께** 보여준다. 폴더를 펴면 그 안의 원고가 이어진다.
  맨 위 줄들이 root의 내용이다 — root 자체는 그리지 않는다
- 현재 원고는 강조하고, 그 조상 폴더는 자동으로 펴 준다
- `⋯` 메뉴: 이름 바꾸기 · 이동 · 복제 · 내보내기 · 삭제
- 접으면 아이콘 띠를 남기지 않고 **통째로 숨긴다.** 글 쓰는 화면이라 좁은 띠가
  남아 있어 봐야 방해만 된다. 여는 버튼은 헤더에 둔다
- **가로·세로 모두 스크롤한다.** 원고가 쌓이면 어차피 세로 스크롤이 필요하고,
  트리가 깊어지면 이름이 잘리는 것보다 가로로 미는 편이 낫다. 이름을 줄임표로
  자르지 않는다

### 헤더의 브레드크럼

사이드바가 있어도 브레드크럼은 남긴다 — 접었을 때 현재 위치를 알 방법이 필요하다.
길어지면 앞을 줄인다: `… / 2026 / 감나무 있는 마당`

### 경로

```
/            → 마지막 원고로. 없으면 온보딩으로 만들어 연다
/w/$id       → 원고 편집
/w/trash     → 휴지통
```

원고 목록 화면을 따로 두지 않는다 — 사이드바가 그 일을 한다. 원고마다 주소가
있으면 뒤로 가기가 원고 전환이 되고, **탭 여러 개에 원고를 각각 띄울 수 있다.**

### 이동은 끌어놓기 대신 고르기로

끌어놓기는 손이 많이 가고 모바일에서 특히 어렵다. 먼저 **`이동` → 폴더 고르기
다이얼로그**로 만든다. 자기 자손은 목록에서 빼서 순환을 애초에 막는다.

끌어놓기는 나중에 얹되 `이동` 메뉴는 남긴다 — 모바일과 키보드 사용자에게 필요하다.

### 휴지통

```
🗑 휴지통                                        [전부 비우기]
─────────────────────────────────────────────────────────
📄 옛 원고            신춘문예 / 2025에 있던 것
                      23일 뒤 삭제     [되살리기] [지금 삭제]
📁 습작 (원고 3편)     신춘문예에 있던 것
                      11일 뒤 삭제     [되살리기] [지금 삭제]
```

- **남은 날을 적는다.** "30일 뒤 삭제"라고만 하면 언제인지 알 수 없다
- 폴더는 **몇 편이 함께 들어 있는지** 보여 준다
- `지금 삭제`와 `전부 비우기`는 되돌릴 수 없으므로 한 번 더 묻는다

### 모바일

사이드바는 왼쪽에서 덮는 서랍으로 연다. 원고를 고르면 닫힌다.
원고/원고지 전환 스위치는 지금처럼 오른쪽 아래에 둔다.

## 5. 반드시 처리할 것

**1. 저장 실패를 삼키지 않는다.** 지금 코드는 디바운스된 타이머 안에서
`localStorage.setItem`을 부르고 결과를 보지 않는다. 상한(5MB)에 닿으면
`QuotaExceededError`가 나는데, **사용자는 계속 쓰고 아무것도 저장되지 않는다.**
원고 관리를 붙이기 전에도 이미 있는 위험이다. 실패하면 분명히 알리고 내보내기를
권한다.

**2. 삭제는 되돌릴 수 있어야 한다.** 서버 사본이 없으니 삭제는 영구 소실이다.
30일 휴지통(1절)과, 되돌릴 수 없는 동작에 대한 재확인.

**3. 탭 두 개가 색인을 동시에 고칠 수 있다.** 각자 다른 원고를 열어도 색인 키는
하나다. 읽고-고치고-쓰는 사이에 다른 탭이 쓰면 덮인다.
- 색인을 쓸 때는 **그 자리에서 다시 읽어 병합**한다
- `storage` 이벤트를 들어 다른 탭의 변경을 사이드바에 반영한다
- 같은 원고를 두 탭에서 열면 막지 않고 **알리기만** 한다

**4. `navigator.storage.persist()`를 부른다.** 지원을 확인했다(`true`). 허용되면
용량 압박 상황에서 브라우저가 함부로 지우지 못한다.

**5. 저장되었음을 보인다.** 원고가 여러 편이 되면 "지금 것이 저장됐나"가 늘
불안해진다. 마지막 저장 시각을 조용히 표시한다.

**6. 색인과 문서가 어긋날 수 있다.** 키가 둘로 나뉘어 있으니 한쪽만 남는 경우가
생긴다.
- **색인에 없는 `doc:<id>`** — 용량만 먹는 고아다. 앱을 열 때 조용히 지운다
  (휴지통에 있는 것은 제외한다 — 되살릴 본문이다)
- **색인에 있는데 본문이 없는 원고** — 빈 문서로 열어 덮어쓰면 안 된다.
  열지 말고 "본문을 찾을 수 없다"고 알린 뒤 그 항목을 지울지 묻는다

**7. 본문을 저장할 때 색인도 함께 갱신된다.** `chars`·`sheets`·`updatedAt`이
색인에 있으므로 저장이 두 키를 건드린다. 원고 200편이어도 색인은 30KB 안팎이라
비용은 문제가 아니지만, **본문과 같은 디바운스로 묶어** 한 번에 쓴다.

---

## 6. 순서

1. **저장 실패 처리 + `persist()`** — 원고 관리와 무관하게 지금 있는 위험이다
2. **저장소 계층 분리** — `src/lib/store/`로 키 조작을 모은다. 지금은 라우트에
   흩어져 있다
3. **마이그레이션 + 온보딩** — 화면은 그대로, 안쪽만 새 구조로. 원고 1편으로 동작
4. **경로 분리** (`/w/$id`)
5. **사이드바 + 폴더 트리**
6. **이동 · 복제 · 삭제(휴지통 30일)**

3번까지 하면 겉보기는 지금과 같고 구조만 바뀐다. 되돌리기 쉬운 지점이다.

## 7. 정해진 것

- 공모전 정보는 넣지 않는다 — 노션과 중복
- 폴더는 중첩 허용, **저장은 materialized path(id 기반)**
- **보이지 않는 root 폴더.** 원고도 폴더도 root에 놓일 수 있고, root는 지워지지
  않는다. 온보딩은 root에 원고 하나만 만든다
- 사이드바는 가로·세로 모두 스크롤. 이름을 자르지 않는다

## 8. 아직 답이 없는 것

- **사이드바 정렬 순서.** 폴더와 원고를 무엇으로 줄 세울지 정하지 않았다.
  이름순이 예측 가능하고, 수정순이 쓰기에 편하다. 수동 정렬은 `order` 필드가
  필요해 지금은 과하다. **폴더는 이름순, 원고는 수정순**을 기본으로 제안한다
- **한 폴더에 원고가 많아질 때.** 수십 편이면 사이드바가 길어진다. 접힘이
  기본이라 당장은 견디지만, 폴더 안 정렬·검색이 필요해질 수 있다
- **원고 복제의 이름.** `제목 (사본)` 정도면 충분하지만, 같은 이름이 여러 개
  생겼을 때 번호를 붙일지는 정하지 않았다
