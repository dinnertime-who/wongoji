# GA4: 비로그인 작성과 로그인 전환

보고 싶은 숫자는 **비로그인 상태에서 실제로 본문을 편집한 사용자 수**와 **그 뒤 로그인에 성공한 사용자 비율**이다. 단순 방문이나 로그인 버튼 클릭을 성공으로 세지 않는다. 신규 가입과 기존 계정 로그인을 구분하는 측정은 아니다.

## 1. GA 속성과 배포 설정

1. Google Analytics에서 GA4 속성을 만들고 보고 시간대를 대한민국, 통화를 KRW로 설정한다.
2. 관리 → 데이터 스트림 → 웹에서 `https://wongo.dinnertimes.app`을 등록한다. 표시되는 `G-…` 측정 ID를 복사한다.
3. 이 스트림의 **향상된 측정을 끈다.** 앱이 SPA 페이지뷰를 직접 전송하므로 자동 페이지뷰/브라우저 기록 추적을 함께 쓰면 중복될 수 있다. 자동 폼·검색·클릭 수집도 사용하지 않는다.
4. 로컬은 `.env.local`에, 배포는 **빌드를 실행하는 환경의 환경 변수**에 아래 값을 넣는다. Cloudflare 런타임의 Worker secret이나 `.dev.vars`만 설정해서는 Vite 클라이언트 번들에 반영되지 않는다.

```dotenv
VITE_GA_MEASUREMENT_ID=G-실제측정ID
VITE_GA_DEBUG=false
```

5. 해당 환경 변수로 다시 빌드하고 배포한다. 기존 GTM/Google tag를 별도로 추가하지 않는다. 측정 ID는 공개 식별자이며 비밀키가 아니다.
6. 탐색에서 더 긴 기간을 비교하려면 관리 → 데이터 보관에서 이벤트 데이터 보관을 14개월로 설정한다. 팀의 접속은 내부 트래픽 필터를 테스트한 뒤 제외한다.

측정 ID가 없거나 형식이 틀리면 아무것도 수집하지 않는다. 개발 모드에서는 기본적으로 꺼져 있다. 배포 미리보기에도 실제 속성 ID를 넣으면 수집되므로, 미리보기는 ID를 비워 두거나 테스트 속성을 사용한다.

페이지뷰 수동 수집과 자동 수집 중복 방지는 [Google 페이지뷰 가이드](https://developers.google.com/analytics/devguides/collection/ga4/views)를 따른다.

## 2. 수집되는 이벤트

| 이벤트 | 발생 조건 | 용도 |
| --- | --- | --- |
| `page_view` | 최초 화면 및 SPA 경로 이동 | 방문 규모 |
| `writing_started` | 본문 편집 후 공백이 아닌 글자가 남아 있는 첫 변경 | 실제 작성 사용자 |
| `login_started` | 구글 로그인 버튼 클릭 | 로그인 시도 및 이탈 |
| `login` | 같은 탭의 로그인 시도 후 30분 이내 인증된 세션 확인 | 로그인 성공 |
| `guest_to_login` | 위 로그인 성공 + 같은 브라우저의 최근 30일 비로그인 작성 이력 | 비로그인 작성 → 로그인 전환 |

`writing_started`는 페이지 실행 동안 로그인 상태별 한 번이다. 타이핑, 붙여넣기, 기존 본문 편집이 포함된다. 초기 내용 복원, 최초 조판, 제목만 변경, 빈 본문에서 빈 행만 추가하는 것은 제외한다. 새로고침 뒤 다시 편집하면 이벤트는 다시 발생하므로 **사람 수는 이벤트 수가 아니라 총 사용자 수(Total users)**로 본다.

로그인 상태로 재방문하거나 로그인 후 새로고침해도 `login`과 `guest_to_login`을 다시 보내지 않는다. 로그인 API 실패는 시도 표시를 지우고, 인증 취소로 비로그인 상태로 돌아오면 성공을 보내지 않는다. 최초 가입도 인증 성공이면 `login`으로 센다. Google의 [권장 login 이벤트](https://developers.google.com/analytics/devguides/collection/ga4/reference/events#login)를 사용한다.

## 3. GA 맞춤 정의와 주요 이벤트

로그인 버튼은 `login_started`의 GA 처리 완료 콜백을 기다린 뒤 인증 요청을 시작한다. 대기는 최대 1초이며, 광고 차단 등으로 태그가 실행되지 않아도 별도 타이머로 로그인을 진행한다. 이 콜백은 네트워크 전송이나 보고서 반영을 보장하는 신호는 아니다. 실제 브라우저 검사에서 일반 이벤트는 콜백 이후에도 약 5초간 배치 대기했고, 즉시 외부로 이동하면 요청이 누락되었다. 따라서 콜백 대기만으로 이 문제가 해결되었다고 판단해서는 안 된다.

관리 → 맞춤 정의 → 맞춤 측정기준에서 다음을 **이벤트 범위**로 만든다.

| 표시 이름 | 이벤트 매개변수 | 값 |
| --- | --- | --- |
| 로그인 상태 | `auth_state` | `guest`, `signed_in` |
| 로그인 시작 화면 | `entry_point` | `/`, `/library`, `/w/:docId`, `/f/:folderId`, `/guide`, `/other` |

`auth_state`는 이벤트가 발생했을 당시의 상태다. 사용자 속성으로 만들면 과거의 비로그인 활동과 현재 로그인 상태를 혼동하기 쉽다. `method=google`도 로그인 관련 이벤트에 전송하지만, 제공자가 하나여서 별도 맞춤 정의는 필요 없다.

관리 → 이벤트에서 `guest_to_login`을 **주요 이벤트**로 지정한다. 아직 목록에 없다면 해당 이름으로 주요 이벤트를 추가하거나 테스트 수집 뒤 지정한다. `login_started`도 **주요 이벤트로 지정**한다. 일반 이벤트의 배치 대기로 로그인 화면 이동 전에 전송이 누락되는 것을 줄이기 위한 설정이다. 주요 이벤트는 즉시 전송된다([Google 이벤트 그룹화 안내](https://support.google.com/analytics/answer/9322688?hl=en)). 목록에 없으면 관리 → 이벤트 → 이벤트 만들기에서 `login_started`를 입력하고, 코드로 만들기를 선택해 주요 이벤트 표시를 켠다. 로그인 성공률은 주요 이벤트 전체 합계가 아니라 **`guest_to_login`만** 사용한다. 맞춤 측정기준을 일반 보고서에서 사용하기까지는 24–48시간이 걸릴 수 있다. [맞춤 측정기준 공식 안내](https://support.google.com/analytics/answer/14239696?hl=ko)

## 4. 매주 볼 보고서

**비로그인 작성 사용자 수:** 탐색 → 자유 형식에서 측정항목 `총 사용자`, `이벤트 수`를 추가한다. 필터를 `이벤트 이름 = writing_started`, `로그인 상태 = guest`로 설정한다. `총 사용자`가 질문의 답이다. 비교하려면 `로그인 상태`를 행으로 넣고 guest 필터를 제거한다. 한 사람이 기간 중 양쪽 상태로 작성할 수 있으므로 두 행의 합은 전체 고유 사용자 수와 다를 수 있다.

**작성 → 로그인 전환율:** 탐색 → 유입경로 탐색에서 닫힌 유입경로를 만든다.

1. `writing_started` AND `auth_state = guest`
2. `guest_to_login`

단계 사이는 **간접적으로 다음 단계로 이어짐**, 전환 제한 시간은 **30일 이내**로 설정한다. 이 유입경로의 완료율을 대표 전환율로 쓴다. 7일 이내 보고서를 복제해 두면 초기 전환 속도도 볼 수 있다. 로그인 클릭을 중간 필수 단계로 넣지 않은 것은 수집 누락 하나 때문에 실제 성공까지 빠지는 것을 줄이기 위해서다.

**로그인 어디서 이탈하는가:** 별도 닫힌 유입경로로 `writing_started (guest)` → `login_started` → `guest_to_login`을 만든다. 간접 순서를 허용하고 마지막 두 단계는 30분 이내로 설정한다. 기기 카테고리로 나누면 모바일과 PC 차이를 볼 수 있다. [GA 유입경로 탐색 안내](https://support.google.com/analytics/answer/9327974?hl=ko)

단순히 이번 주 `guest_to_login` 사용자 ÷ 이번 주 `writing_started` 사용자를 계산하면 지난주에 쓰고 이번 주 로그인한 사람이 분자에만 들어갈 수 있다. **같은 유입경로에 들어온 집단의 완료율**을 사용하고, 작성과 전환이 모두 포함되는 조회 기간을 잡는다. 최근 유입자는 아직 30일을 다 기다리지 않았으므로 이전 집단과 비교할 때 관찰 기간도 맞춘다.

## 5. 검증

테스트용 GA 속성을 권장한다. `.env.local`에서 테스트 ID와 `VITE_GA_DEBUG=true`를 설정하고 개발 서버를 재시작하면 로컬에서도 수집된다. GA 관리 → DebugView와 브라우저 Network의 `g/collect` 요청을 함께 확인한다.

1. 로그아웃 상태로 `/` 접속: `page_view`만 발생. 저장된 본문을 복원해도 작성 이벤트가 없어야 한다.
2. 본문에 글 입력 또는 붙여넣기: `writing_started`, `auth_state=guest`. 계속 입력해도 반복되지 않는다.
3. 구글 로그인 클릭: `login_started`. 취소하면 성공 이벤트가 없어야 한다.
4. 다시 시도해 로그인 완료: `login`, `guest_to_login` 각각 한 번. 돌아온 화면이 `/library` 또는 원고여도 동일하다.
5. 로그인 후 새로고침: 성공 이벤트가 추가되지 않는다. 계정 원고를 편집하면 `writing_started`, `auth_state=signed_in`.
6. 다른 원고·폴더로 이동: `page_view` 한 번씩. 전송 주소에는 원고/폴더 ID, 쿼리, 해시가 없어야 한다.
7. QA가 끝나면 `VITE_GA_DEBUG=false`로 되돌린다. 운영 ID는 운영 빌드에만 넣는다.

자동 테스트는 GA 초기화·중복 방지·OAuth 전후 이력·실패/만료·저장소 차단·SSR·주소 정제를 확인한다. 실제 GA 도착과 구글 인증 왕복은 실제 측정 ID 및 계정으로 위 절차를 확인해야 한다.

## 측정 범위

본문·제목·이메일·이름·계정 ID는 보내지 않는다. 원고/폴더 URL은 형태만 남기고, referrer는 외부 출처의 origin 또는 정제한 내부 경로만 보낸다. 검색 쿼리와 UTM도 제거하므로 캠페인별 분석은 현재 범위에 포함되지 않는다. GA의 기본 브라우저 식별 쿠키를 사용하며 앱 자체 User-ID는 보내지 않는다. Google signals와 광고 개인화 신호는 비활성화한다.

브라우저 localStorage에는 마지막 비로그인 작성 시각, sessionStorage에는 로그인 시도 시각만 저장한다. 각각 30일/30분이 지나면 판정에서 제외한다. 전환 성공 시 작성 표시와 시도 표시를 지운다. 로그인 시도 표시는 같은 탭의 OAuth 이동을 전제로 한다.

따라서 이 수치는 같은 브라우저에서 관측된 사용자 기준이다. 광고 차단·쿠키/저장소 삭제·다른 기기·다른 탭에서 완료한 로그인·네트워크 누락으로 실제 사용자보다 적게 잡힐 수 있고, 한 사람이 여러 브라우저를 쓰면 여러 사용자로 잡힌다. 현재 코드는 유효한 ID가 있으면 태그를 로드하며 별도 동의 UI를 추가하지 않는다. 서비스의 분석 쿠키 동의 정책에 따라 필요하면 태그 로딩 전에 동의 상태를 연결해야 한다.
