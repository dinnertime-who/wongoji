# 계획 — 오프라인

> 작성: 2026-08-13. 계정 보관함을 서버 정본으로 옮긴 직후
> ([plan-server-first.md](plan-server-first.md))의 다음 걸음.

## 0. 우리는 노션이 아니다 — 그것이 설계를 정한다

오프라인 얘기는 대개 노션·리니어 같은 것을 흉내 내는 데서 시작하는데, 그쪽이
치르는 값의 대부분은 **우리에게 없는 문제**를 푸느라 드는 것이다.

| 그쪽에 있는 것 | 우리 | 그래서 빠지는 것 |
|---|---|---|
| 블록 트리 | 원고 한 편이 단위 | 필드 경로 단위 연산, 블록별 버전 |
| 권한 상속 | 한 사람 = 한 보관함 | 오프라인 권한 캐시, 조상 사슬 검사 |
| 미디어 | 전부 텍스트 JSON | 큰 바이너리 캐시·업로드 재개 |
| 동시 편집 | 혼자 쓴다 | **CRDT·OT, 실시간 수렴** |

넷째가 제일 크다. **우리에게 필요한 것은 병합이 아니다.** 두 사람이 한 문단을
동시에 치는 일이 없으므로, 풀어야 할 문제는 "같은 원고를 **다른 때** 두 기기에서
이어 썼다" 하나뿐이고 그것도 드물다.

여기에 하나를 보탠다. **원고는 덧붙여 쓰는 글이다.** 소설을 두 갈래로 고쳤다면
그건 병합할 대상이 아니라 **두 편의 원고**다. 문단 단위로 자동 병합해서 내놓은
원고는 사람이 쓴 적 없는 글이고, 그것이 원본을 덮으면 되돌릴 수 없다.

> **잃지 않는 것이 첫째, 깔끔한 것이 둘째.** 사본이 하나 더 생기는 것은 사소한
> 불편이고, 문단이 사라지는 것은 이 앱의 존재 이유가 무너지는 일이다.

## 1. 뼈대 — 이미 절반은 되어 있다

서버 정본으로 옮기면서 두 가지가 생겼고, 그것이 그대로 오프라인의 뼈대다.

- **연산(`ArchiveOp`)** — 색인 변경이 직렬화 가능한 값이고 순서가 있다
- **`applyOp`** — 서버와 브라우저가 나눠 쓰는 순수 함수

그래서 오프라인은 새 구조가 아니라 **지금 하는 일을 하나에서 N개로 늘리는 것**이다.

```
보이는 색인 = pendingOps.reduce(applyOp, baseIndex)

baseIndex    서버에서 마지막으로 받은 것        (IndexedDB)
pendingOps   아직 못 보낸 연산들, 순서대로      (IndexedDB)
```

낙관적 갱신이 지금 연산 하나를 미리 적용하는 그 계산이다. 큐가 비면 지금과
똑같이 동작한다 — **오프라인 코드가 온라인 경로를 갈아엎지 않는다.**

연결되면 큐를 앞에서부터 하나씩 보낸다. 성공한 것은 빼고, 서버가 돌려준 색인이
새 `baseIndex`가 된다.

---

## 2. id를 클라이언트로 되돌린다

지금은 서버가 발급한다. 오프라인에서는 물어볼 데가 없으므로 되돌려야 한다.

- **id는 이미 cuid2로 갈아 두었다.** 암호학적 난수 + 기기 지문 + 카운터라
  서로 모르는 기기들이 각자 만들어도 부딪히지 않는다. 열여섯 자로 줄여 쓰는데,
  폴더 id가 경로 문자열에 박히기 때문이다(mpath) — UUID(36자)는 세 겹만 깊어져도
  읽을 수 없다
- **서버는 거부하지 않고 다시 매겨 준다.** 받은 id가 이미 쓰였거나 자취에 있으면
  새 id를 주고 응답에 `remapped: { 옛것: 새것 }`을 실는다. 클라이언트가 큐와
  화면에서 갈아 끼운다. `remapIds`가 이미 그 일을 한다(경로까지 고친다)
- 거부하면 오프라인에서 쓴 원고가 갈 곳을 잃는다. **되살릴 수 없는 답을 서버가
  내놓아서는 안 된다.**

이러면 만드는 연산도 낙관적으로 그릴 수 있게 된다 — 지금 왕복 한 번을 기다리는
그 자리가 함께 없어진다.

---

## 3. 큐를 재생할 때 — 대상이 사라졌으면

다른 기기에서 지운 원고를, 이 기기가 오프라인에서 고쳤다. `applyOp`는 대상이
없으면 색인을 그대로 돌려주므로 **조용히 버려진다.** 그것이 맞는 경우와 아닌
경우를 가른다.

| 밀린 것 | 대상이 없으면 |
|---|---|
| 이름 바꾸기 · 옮기기 · 차례 · 버리기 · 되살리기 | **버린다.** 없는 것에 대고 한 일이라 뜻이 없다 |
| 제목 · 목표 고치기 | 버린다 |
| **본문 쓰기** | **절대 버리지 않는다** — 아래 |

본문이 갈 곳을 잃었으면 **새 원고로 되살린다.** 제목에 표시를 붙이고 맨 위에
놓는다. 이유는 1절에 적은 그것이다 — 사본 하나와 사라진 원고 중에 고르는 문제다.

```
"감나무 있는 마당 (되살린 원고)"
```

---

## 4. 본문이 갈라졌을 때 — 병합하지 않고 가른다

두 기기가 같은 원고를 각각 고쳤다. 지금은 나중에 보낸 쪽이 이긴다(= 앞의 것이
사라진다). 오프라인이 생기면 이 창이 몇 시간으로 늘어나므로 그대로 둘 수 없다.

**본문 행에 판 번호를 둔다.** 받을 때 함께 받아 두었다가 보낼 때 같이 보낸다.

```
PUT /api/archive/doc/:id   { content, base: 17 }
  → 서버 판이 17이면 쓰고 18을 돌려준다
  → 아니면 409 + 서버의 지금 본문
```

409를 받으면 **가른다.**

```
서버 것은 그대로 둔다
내 것을 새 원고로 만든다 — "감나무 있는 마당 (충돌 사본 · 8월 13일)"
배너: "같은 원고를 다른 기기에서도 고쳤습니다. 두 벌을 모두 남겼습니다."
```

여기서 CRDT를 쓰지 않는 근거를 한 번 더 적어 둔다. 얻는 것은 "자동으로 하나가
된다"인데 **우리에게는 그 하나가 아무도 쓰지 않은 글이다.** 치르는 값은 본문보다
큰 메타데이터, 조판 엔진이 보는 `Block` 구조의 오염, 그리고 되돌릴 수 없는
자동 결정이다. 셈이 맞지 않는다.

---

## 5. 무엇을 미리 받아 두나

- **색인은 통째로.** 원고 200편에 57KB다. 아낄 것이 없다
- **본문은 연 적 있는 것만.** 6MB를 다 받을 이유가 없고, 실제 시나리오는
  "쓰던 원고를 비행기에서 이어 쓴다"이다. 연 원고가 저절로 남으면 그것으로 족하다
- **"오프라인용으로 받아 두기" 단추를 두지 않는다.** 사람에게 미리 정하라고
  묻는 설정이고, 대개 틀리게 답한다. 열었으면 남는다 — 규칙이 하나면 설명할
  것도 없다

용량 상한은 두지 않는다. 원고는 작고, 지우는 규칙을 두면 "지웠는데 오프라인에서
필요했던" 경우가 생긴다. 대신 `navigator.storage.persist()`에 기댄다(이미 있다).

---

## 6. 화면 — 여기가 오프라인의 성패다

오프라인 기능이 실패하는 방식은 대개 하나다. **저장된 줄 알았는데 아니었다.**

- 머리말에 상태 하나 — `저장됨` · `이 기기에만 있음 3` · `보내는 중`
- **오프라인은 오류가 아니다.** 지금 `SaveErrorBanner`가 붉은 배너로 알리는데,
  연결이 없는 것은 사용자가 고칠 일이 아니다. 조용한 표시로 낮추고 **미전송
  개수**를 늘 보이게 한다
- 다른 기기를 열기 전에 "여기 아직 안 올라간 것이 있다"를 알 수 있어야 한다.
  이것이 오프라인에서 사람이 실제로 잃는 지점이다

## 7. 단계

### 0. 앱이 오프라인에서 뜨기는 해야 한다

서비스 워커로 앱 셸을 캐시한다. **이것이 없으면 나머지가 전부 무의미하다** —
연결이 없으면 페이지 자체가 안 뜬다. 데이터 설계와는 별개의 작업이라 먼저,
따로 한다.

### 1. id를 클라이언트로

열두 자 발급 · 서버 재매김 응답(`remapped`) · 만드는 연산도 낙관적으로.
이 단계만으로도 새 원고·새 폴더의 왕복 지연이 없어진다.

### 2. 색인 캐시와 연산 큐

`baseIndex` + `pendingOps`를 IndexedDB에. 화면은 `reduce(applyOp)`.
재생 규칙(3절)까지. 큐가 비면 지금과 같다.

### 3. 본문 판 번호와 가르기

`archive_doc_content.version` · `PUT`에 `base` · 409 → 충돌 사본.
서버가 판을 세기 시작하는 것이 먼저다.

### 4. 상태 표시

미전송 개수 · 조용한 오프라인 표시 · 배너 등급 낮추기.

---

## 8. 안 하는 것

- **실시간 협업** — 혼자 쓰는 앱이다
- **문자 단위 병합(CRDT·OT)** — 4절
- **오프라인에서 계정 바꾸기** — 세션이 있어야 어느 보관함인지 안다
- **오프라인에서 내보내기 서버 의존** — 지금도 브라우저에서 만든다. 그대로 둔다
